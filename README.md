# fuel-lattice-ml

Machine learning prediction of lattice parameters for nuclear fuel solid-solution
compositions (U(N,C), (Ce,Nd)O2, and other two-component mixed systems), trained on the
full Materials Project database.

**Status: private repository, pending ORNL software-release approval.** See
`PUBLICATION_CHECKLIST.md`.

---

## Quickstart

A fresh clone needs **no Materials Project API key** to get a working prediction
pipeline, because the post-query resume point ships pre-committed
(`Data/MP_Dataset_Original_Trimmed.csv`, 21 MB):

```bash
git clone <this-repo>
cd fuel-lattice-ml
uv venv --python 3.12 .venv
uv pip install --python .venv/Scripts/python.exe -r requirements.txt   # Windows
# uv pip install --python .venv/bin/python -r requirements.txt         # Unix

cp .env.example .env
# Edit .env and set HF_TOKEN=<your token> (needed only to fetch the model — see below)

python scripts/fetch_models.py          # downloads Models/binaries/DependentRFModel.joblib (~4 GB)
python cli.py predict --composition "UN0.5C0.5"
```

If you'd rather train from scratch instead of fetching the binary:

```bash
python cli.py build --resume    # ~9 minutes — featurization only, no MP query
python cli.py train --fast      # ~10 minutes — trains rf1 (Dependent RF)
python cli.py predict --composition "UN0.5C0.5"
```

Only a **forced** re-query of Materials Project (`cli.py build --force`) is a
multi-hour job, and only that path needs `MP_API_KEY` in `.env`.

## What this is

Four core notebooks at the repository root walk through the pipeline end-to-end and
are narrated for learning; **every notebook imports from `engine/`** rather than
defining its own hyperparameters, so there is exactly one place hyperparameters live
(`engine/train_models.py`'s `model_estimators()`), pinned by
`tests/test_params_parity.py`:

1. `FuelLatticeParameterDataFeaturization.ipynb` — query Materials Project, extract
   symmetry, matminer-featurize.
2. `FuelLatticeParameterModelCreation_CrossVal.ipynb` — full-dataset model fitting +
   5-fold cross-validation.
3. `FuelLatticeParameterModelPrediction.ipynb` — predict against experimental benchmark
   compositions.
4. `FuelLatticeParameterModelOptimization.ipynb` — per-crystal-system /
   per-lattice-threshold accuracy sweep.

`exploratory/` holds five additional, **unmaintained** notebooks from earlier
experimentation (neural network, symbolic regression, an alternate train/test split,
etc.) — see `exploratory/README.md` before relying on any of them.

## Repository layout

```
engine/            the actual ML pipeline — single source of truth for everything
cli.py              command-line entry point: status | build | train | evaluate | predict
server.py           FastMCP stdio server exposing predict + status as MCP tools
.mcp.json           registers the MCP server for Claude Code
.claude/skills/      lattice-predict, lattice-build, lattice-train, lattice-evaluate
Data/                committed inputs: the build seed, curated references, benchmarks
Dataset/             GENERATED, gitignored — regenerated by `cli.py build`
Models/              model cards, hyperparameters, metrics (committed); binaries fetched separately
Results/             the optimization study, cross-validation metrics, figures
exploratory/         unmaintained notebooks — see exploratory/README.md
scripts/             fetch_models.py, upload_models.py, write_model_manifest.py
tests/               pytest suite, incl. the hyperparameter-parity + seed-resume guards
```

## Using it as an agent tool

This repository is also a self-contained MCP tool: `.mcp.json` at the root registers a
`lattice-prediction` server exposing `predict_lattice_parameter` and `artifact_status`,
and `.claude/skills/` ships four skills (`lattice-predict`, `lattice-build`,
`lattice-train`, `lattice-evaluate`) that a Claude Code agent can use directly —
`/lattice-predict UN0.5C0.5`. Clone this repo (standalone, or as a git submodule of a
larger agent project) and both the notebooks and the agent tooling stay in sync,
because they're the same `engine/` code.

## Model summary

| Key | Name | Status |
|---|---|---|
| `rf1` | Dependent RF | **trained** — the model shipped in this repository |
| `rf2` | Independent RF | not trained |
| `gbr1` | Dependent GBR (XGBoost) | not trained |
| `gbr2` | Independent GBR (HistGBR) | not trained |
| `lin` | Linear Regression | not trained (baseline only, never reported) |

`rf1` is the headline model because it is the **only** trained model in this
repository — not because a comparative accuracy ranking has been established. See
`Models/DependentRFModel/model_card.md` for its actual cross-validated metrics
(5-fold CV, cubic subset: R² ≈ 0.977, MAE ≈ 0.122 Å).

## Fetching the model binary

`Models/binaries/DependentRFModel.joblib` (3.97 GB) is **not** in git — see the root
`.gitignore`. It's hosted on HuggingFace and fetched via:

```bash
python scripts/fetch_models.py
```

This requires `HF_TOKEN` in `.env` while the HuggingFace repo is private (see
`PUBLICATION_CHECKLIST.md`). The script verifies the download's SHA-256 against
`Models/MANIFEST.json` **before** it is ever unpickled — see `Models/README.md` for why
that matters.

Loading uses `joblib.load(path, mmap_mode="r")`, which is required (not optional) to
avoid ~1,800 spurious `DeprecationWarning`s from joblib's ndarray reconstruction path —
see `Models/README.md` for the full explanation. Predicting with `rf1` needs
**~4.5 GB free RAM**.
